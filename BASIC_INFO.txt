- Add questions manually to the set
- Grant access: select student(s) + set attempt limit (1, 2, 3...n)
- Dashboard: view all student logs, scores, AI confidence per answer
4. Student Module
- Login → see only sets they've been granted access to
- See remaining attempts (from `access_grants`)
- Submit answer → decrement `attempts_used`, block if limit reached
- View score + explanation after grading
5. Knowledge Base / "Notebook-style" Retrieval (core AI part)
This is your NotebookLM-like feature — Retrieval-Augmented Generation (RAG):
When teacher uploads materials → extract text (PDF/DOCX parsing)
Split text into chunks (~500 words) → convert to embeddings (vector representation)
Store embeddings in a vector database (Chroma, FAISS, or Pinecone)
When a student submits an answer, retrieve the most relevant chunks from that set's materials using similarity search
Feed those chunks + student's answer to the LLM to validate against teacher's own material, not just the open web
6. Validation Priority Logic (fallback chain)
1. Teacher materials exist for this set? → Use RAG (step 5) as primary source
2. If no materials OR low-confidence match → Query verified AI (Claude/GPT/Gemini API) 
   with web search grounding if available
3. If AI API fails/unavailable → Fallback to local dataset comparison 
   (e.g., pre-stored Q&A dataset, cosine similarity on embeddings)
Each path logs which `source_used` was applied — important for your project report/demo.
7. Scoring Engine
- Prompt the LLM to return strict JSON:
json
{"score": 8, "max_score": 10, "correct": true, "explanation": "...", "confidence": 0.87}
- Parse this server-side, store in `logs` table
8. Logging Module
- Every submission logs: question, student answer, AI/RAG response, score, source used, timestamp
- Teacher dashboard queries this table for analytics (avg score, most-missed questions, per-student history)

Threading & Synchronization (the OS part)
This is where you demonstrate real OS concepts:
1. Thread pool for validation calls — AI API calls are slow (network latency); running them in a pool keeps the app responsive:
python
from concurrent.futures import ThreadPoolExecutor
executor = ThreadPoolExecutor(max_workers=4)
future = executor.submit(validate_answer, question, answer, set_id)
2. Lock for shared resources — prevents race conditions when two requests touch the same data (e.g., a student double-submitting, or two writes to the log at once):
python
attempt_lock = threading.Lock()

def use_attempt(student_id, set_id):
    with attempt_lock:              # critical section
        grant = get_grant(student_id, set_id)
        if grant.attempts_used >= grant.max_attempts:
            return False
        grant.attempts_used += 1
        db.session.commit()
        return True
Run Flask with `threaded=True` so this concurrency actually matters. In your report, this maps directly to mutual exclusion / critical section / race condition avoidance — good talking points for viva.
